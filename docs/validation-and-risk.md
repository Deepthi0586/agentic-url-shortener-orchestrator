In short: I hit a couple of real bugs while building this — API billing
running out mid-run, and the AI silently generating nothing useful for
a while — and instead of just patching around them, I dug into why
they happened and fixed the actual cause. Details below.

# Validation and Risk Control

This document identifies risks and failure scenarios in the system and
describes how each is validated against or guarded against — per Core
Requirement 6 of the assessment. Where possible, this references an
actual tested run rather than a hypothetical, so each control is
evidenced, not just claimed.

## 1. External LLM API failure

**Risk:** Any stage calling Claude (Requirements, Design, etc.) depends on
an external network service. That service can fail for reasons outside
the orchestrator's control — billing/quota exhaustion, rate limiting,
network timeouts, or a transient outage.

**Guardrail:** `LlmClient` (see `orchestrator/.../llm/LlmClient.java`)
raises an exception on any non-200 response rather than silently
returning empty or partial data. `OrchestratorEngine`'s bounded-retry
policy (max 2 retries per stage) picks this up automatically — I didn't
need to write any special retry logic just for LLM calls, since the
retry mechanism already treats any stage failure the same way, no
matter what caused it (see `docs/orchestration-design.md`, section 5).

**Evidence (real, not simulated):** a run was executed against a live
Anthropic API account with an empty credit balance. The Requirements
stage:
1. Attempted the call — failed with `HTTP 400: "Your credit balance is
   too low to access the Anthropic API"`
2. Retried automatically — failed again, same error
3. Retried a second time — failed again
4. After exhausting the retry budget (3 total attempts), the stage
   transitioned to `FAILED` and the engine halted (safe-stop) — no
   further stages attempted to run against the failed dependency
5. The final run summary correctly reported `requirements: FAILED` and
   every dependent stage (`design`, `implementation`, `testing`,
   `documentation`, `release_readiness`) as `PENDING`, never started

This confirms bounded retries and safe-stop work correctly against a
genuine external failure, not just a contrived one.

## 2. LLM output is not valid JSON

**Risk:** Stages ask Claude to respond in a specific JSON shape, but
LLM output is not schema-enforced by the API — the model could return
prose, malformed JSON, or JSON wrapped in unexpected formatting.

**Guardrail:** `LlmClient.completeAsJson()` strips common markdown code
fences before parsing, and wraps the parse attempt in a try/catch that
raises a clear exception (including the raw response for debugging)
rather than passing malformed data downstream. This exception is caught
by the same bounded-retry mechanism as any other stage failure — an
unparseable response is treated identically to a network failure, and
retried up to the same limit before safe-stopping.

## 3. Design stage scope drift

**Risk:** An LLM-generated design could introduce functionality never
requested — e.g., adding authentication or extra endpoints not in the
original requirement.

**Guardrail:** per `docs/orchestration-design.md` section 3, the Design
stage's exit gate requires every element of its output to trace back to
something in the Requirements stage's normalized spec. (Implementation
status: gate logic defined in design; automated trace-back validation
is a planned enhancement — currently enforced via human review at the
Design approval checkpoint, which is itself a required control per
Core Requirement 7, Controlled Autonomy.)

## 4. Generated code contains secrets or unsafe patterns

**Risk:** Code generated by an LLM could hardcode credentials, disable
security checks, or introduce other unsafe patterns without an operator
noticing, especially under time pressure.

**Guardrail:** flagged in the Design stage's policy guardrails (section
7 of the orchestration design) as an explicit exit-gate check before
Implementation is allowed to proceed. Human approval at the Design and
Release Readiness checkpoints provides a second layer of review before
any generated code is considered final.

## 5. Human approval fatigue / rubber-stamping

**Risk:** A reviewer who approves every checkpoint without genuinely
reviewing output defeats the purpose of controlled autonomy — the
system would then be no safer than fully autonomous execution.

**Guardrail:** this is a process risk, not a code risk, and is
acknowledged as a limitation rather than something the software can
fully solve. Mitigations: each approval checkpoint prints the stage's
full output before prompting (not just a yes/no with no context), and
the decision log requires an explicit reason for `reject` and a note
for `revise`, which at minimum requires the reviewer to articulate
something rather than approving silently.

## 6. Single point of failure: no distributed/multi-instance execution

**Risk:** the orchestrator runs as a single process with in-memory
parallel execution (via `CompletableFuture`) — it is not distributed
across machines, and a crash mid-run loses in-memory state beyond the
last saved checkpoint.

**Guardrail:** state is persisted to disk after every round (not just
at the end), so a crash loses at most one round's worth of progress,
not the whole run. This is an accepted trade-off for a prototype scoped
to a single developer's machine — noted here as a known limitation
rather than solved, consistent with the assessment's expectation that
limitations be stated explicitly rather than hidden.

## 7. LLM silently produces no usable output (extended thinking + truncation)

**Risk:** An LLM call can return HTTP 200 (success) while still producing
no usable answer — either because internal reasoning consumes the
entire token budget before any answer is written, or because a large
response is cut off mid-generation, breaking the expected JSON
structure. Both are silent failure modes: no error is raised by the
API itself, so a naive integration could treat them as success.

**Evidence (real, not simulated):** during development, the
Implementation stage (which asks Claude to generate multiple Spring
Boot source files) initially returned completely empty text on every
attempt. Inspecting the raw HTTP response body directly showed why:
```json
"content":[{"type":"thinking","thinking":"","signature":"..."}],
"stop_reason":"max_tokens",
"output_tokens_details":{"thinking_tokens":4096}
```
Extended thinking had used the entire 4096-token budget internally,
leaving nothing for the actual answer. After disabling extended
thinking explicitly (`"thinking": {"type": "disabled"}`) and raising
the token budget, a second, related failure appeared: generating many
files in one response still occasionally exceeded the token limit
mid-JSON, breaking the parse.

**Guardrail:**
- `LlmClient` now explicitly disables extended thinking on every
  request and raises an exception (rather than returning silently) if
  extracted text is ever blank — surfacing this failure mode loudly if
  it recurs, instead of succeeding with nothing.
- `ImplementationStage`'s prompt was scoped down (a hard cap on file
  count, explicit exclusion of out-of-scope features) so the response
  reliably fits the token budget, rather than relying on an
  unboundedly large single response.
- Both fixes are covered by the same bounded-retry / safe-stop
  mechanism as any other stage failure — no special-case handling was
  needed once the underlying `complete()` method correctly raises an
  exception instead of returning empty text.

This is also why the Testing stage's compile-failure path (section 1
above's sibling case) matters: if generated code doesn't compile, that
is treated as a genuine stage failure, not silently reported as
"0 tests passed."

## 8. Trade-off: JSON file state vs. a real database

Addressed in full in `docs/orchestration-design.md`, section 8. Restated
briefly here as a risk-framing: the trade-off accepted is that
concurrent multi-run access (e.g., two runs writing to the same file)
is not safeguarded against, since the access pattern in this prototype
is always one run at a time. This would need to change if the
orchestrator were extended to support concurrent runs.
